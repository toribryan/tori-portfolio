Chat composer is the box people write messages in. It's a set of parts around
one draft, not one component with a prop for every case: each chat surface
picks the parts it needs, puts them in its own order, and adds its own
elements beside them.

<Exhibit
  of="chat-composer.WithAttachments"
  title="Chat composer"
  description="Type and press Enter to send. Shift+Enter breaks the line, and files dropped on it attach."
>
<ExhibitCode label="Install">

```bash
npx shadcn@latest add https://fibo.toribryan.com/r/chat-composer.json
```

It installs fibo's Button and Tooltip with it, plus the `--input-subtle`
and `--ring-subtle` tokens.

</ExhibitCode>
<ExhibitCode label="Usage">

```tsx
import {
  ChatComposerCommonActions,
  ChatComposerFooter,
  ChatComposerFrame,
  ChatComposerInput,
  ChatComposerSubmit,
  LocalChatComposerProvider,
} from "@/components/ui/chat-composer"

export function ChannelComposer() {
  return (
    <LocalChatComposerProvider onSubmit={({ value }) => sendMessage(value)}>
      <ChatComposerFrame>
        <ChatComposerInput placeholder="Message #design" />
        <ChatComposerFooter>
          <ChatComposerCommonActions />
          <ChatComposerSubmit />
        </ChatComposerFooter>
      </ChatComposerFrame>
    </LocalChatComposerProvider>
  )
}
```

When a surface needs something the parts don't do, write it as JSX beside
them rather than adding a prop to a part.

</ExhibitCode>
<ExhibitCode label="State">

Every part talks to this interface and nothing else. Render
`ChatComposerProvider` with your own `state` and `actions` and the same parts
run on them. Custom parts read it with `useChatComposer()`.

```ts
type ChatComposerState = {
  value: string
  attachments: ChatComposerAttachment[]
  submitting?: boolean
  disabled?: boolean
  canSubmit?: boolean // defaults to having text or an attachment
}

type ChatComposerActions = {
  setValue: (value: string) => void
  addAttachments: (files: File[]) => void
  removeAttachment: (id: string) => void
  submit: () => void
}

type ChatComposerAttachment = {
  id: string
  name: string
  size?: number // bytes
  file?: File
}
```

</ExhibitCode>
</Exhibit>

## Anatomy

A provider holds the draft and renders nothing. Every other part reads it
from context, so they work in any order and anywhere below it.

### Edit message

Editing a sent message: a header says so, the footer swaps the actions for
Cancel and Save, and Escape cancels through the text box's own `onKeyDown`.
No `isEditing` prop.

<Exhibit of="chat-composer.EditMessage" description="Save, then press Edit to bring it back.">
<ExhibitCode>

```tsx
<ChatComposerHeader>
  <PencilIcon />
  Editing message
</ChatComposerHeader>
<ChatComposerInput
  aria-label="Edit message"
  onKeyDown={(event) => event.key === "Escape" && cancel()}
/>
<ChatComposerFooter className="justify-end gap-2">
  <Button variant="ghost" onClick={cancel}>Cancel</Button>
  <ChatComposerSubmit>Save</ChatComposerSubmit>
</ChatComposerFooter>
```

</ExhibitCode>
</Exhibit>

### Submit outside the frame

A forward dialog whose Forward button sits in the dialog's footer, outside the
frame. It sends because it's inside the provider, and `canSubmit` lets an
empty note through.

<Exhibit of="chat-composer.SubmitOutsideTheFrame">
<ExhibitCode>

```tsx
<LocalChatComposerProvider canSubmit={() => true}>
  <ChatComposerFrame>
    <ChatComposerInput placeholder="Add a note (optional)" />
  </ChatComposerFrame>
  <ChatComposerSubmit>Forward</ChatComposerSubmit>
</LocalChatComposerProvider>
```

</ExhibitCode>
</Exhibit>

### Synced draft

Two composers on one store, as a draft synced between a laptop and a phone
would be. Type in either one. The parts are the same; only the provider
changed.

<Exhibit of="chat-composer.SyncedDraft">
<ExhibitCode>

```tsx
function SyncedComposerProvider({ children }) {
  const state = useSyncExternalStore(draft.subscribe, draft.get)
  const actions = useMemo(() => createDraftActions(draft), [])
  return (
    <ChatComposerProvider state={state} actions={actions}>
      {children}
    </ChatComposerProvider>
  )
}
```

</ExhibitCode>
</Exhibit>

## Usage

<UsageGuidelines
  guidelines={[
    "Compose a variant from parts instead of adding a prop. An edit box, a thread reply and a forward dialog are three compositions of the same parts.",
    <>
      Keep state out of the parts. If the draft has to survive a reload or
      follow someone across devices, swap <code>LocalChatComposerProvider</code>{" "}
      for a <code>ChatComposerProvider</code> fed by your store.
    </>,
    <>
      Put the provider around everything that needs the draft. A send button in
      a dialog's footer, outside the frame, still works when it's inside the
      provider.
    </>,
    <>
      Leave <code>ChatComposerCommonActions</code> out when a composer needs a
      different set, and list the actions it does need.
    </>,
    <>
      Return a promise from <code>onSubmit</code> when sending takes a round
      trip. The send button shows it's busy, and a rejection keeps the draft.
    </>,
  ]}
/>

## Accessibility

| Key                           | Does                                     |
| ----------------------------- | ---------------------------------------- |
| <Kbd>↵</Kbd>                  | Sends the draft                          |
| <Kbd>Shift</Kbd> <Kbd>↵</Kbd> | Breaks the line                          |
| <Kbd>Tab</Kbd>                | Moves to the actions and the send button |
