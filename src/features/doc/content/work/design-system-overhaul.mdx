## Working inside the old system

When I took over the design system, I started by counting what was in it. I
went through the library by hand, listed every variant of every component, and
checked how many of them appeared anywhere in the product. Very few did.

<Numbered>
  <Item title="No semantic tokens.">
    Tokens were named after their values, such as blue-500, and never after
    their jobs. No product could change its look without editing components,
    and every color choice meant looking one up.
  </Item>
  <Item title="Product logic inside components.">
    Some components knew which product they were in. A component like that
    can't be reused, only copied.
  </Item>
  <Item title="Variants for needs nobody had.">
    Hundreds of combinations had never been placed on a screen, and each one
    still had to be maintained.
  </Item>
  <Item title="No shared names.">
    Three components called the same property three different things, so
    learning one taught you nothing about the next.
  </Item>
  <Item title="Color never checked for contrast.">
    Accessibility was a review at the end of a project, when fixing it cost the
    most.
  </Item>
  <Item title="Nobody deciding what belonged.">
    Anyone could add to the system, and nobody could say no.
  </Item>
</Numbered>

## The variant count

| Component | Before | After | Change |
| --------- | -----: | ----: | -----: |
| Button    |  1,160 |   480 |   −59% |
| Card      |    587 |    32 |   −94% |

The card had 587 variants because designers had no way to build a new card
from parts. Each time someone needed one, they added a variant. The count
measures how often people worked around the system they were meant to use.

<VariantWall />

The cause was the component's switches. Every new need became one more on/off
option, and options multiply: ten of them allow over a thousand cards.

<SwitchSprawl />

## Handoff documents filled the gaps

Designers wrote long handoff documents for every feature. They were slow to
write and slow to read. Engineering didn't work in Figma Dev Mode, so designers
wrote down everything a well-built component would have shown on its own. The
documents were doing the design system's job.

## Pitching the rebuild

Patching would have kept every one of these problems. I pitched a full rebuild,
and made the case together with our front-end lead, each of us speaking for our
own discipline.

<Sides>
  <Side label="Design" title="What I argued">
    - Every product surface gets the same polished design language
    - Designers stop spending time and energy rebuilding the same things
    - Standards get set, and someone's job is keeping them
  </Side>
  <Side label="Engineering" title="What our front-end lead argued">
    - Better version control
    - Components that are easier to implement
    - Less time from idea to release
  </Side>
</Sides>

## Building from the tokens up

I built in layers: tokens, then foundations, then base components, then the
larger components made from them. Each layer uses only the one below it, so a
change at the bottom reaches everything above.

### Tokens

I rebuilt the tokens before I touched a component. Every component takes its
color, spacing and type from them, so fixing components first would have meant
fixing them twice.

Each new token names a job. A button asks for the action color and gets
whichever green the theme has set.

<TokenRoles />

To change a theme, you change a handful of values. No component code changes.

<ThemeSwap />

Our engineers build everything in-house, so I also wrote the CSS framework the
tokens live in. It uses the same names as the Figma library, so designers and
engineers describe the system in the same words.

### Foundations and accessibility

Color, type and spacing came next. I set WCAG AAA as the standard and checked
every color pair for contrast as I defined it, so the palette is accessible
before anyone uses it. Every component carries an accessibility contract from
its first version, and tests on our component documentation site check that it
holds.

### Three rules

A rebuild fixes the system as it stands. To keep it from drifting back, I wrote
three rules and held every component to them.

<Principles>
  <Principle title="No product logic in components">
    If a component knows which product it is in, it isn't a system component.
    That knowledge belongs to the screen that uses it.
  </Principle>
  <Principle title="Build only for real use">
    An option or variant goes in when someone needs it on a screen.
  </Principle>
  <Principle title="Start from the system, and let it grow">
    Designers begin from the shared library, never a blank file. When a pattern
    keeps turning up in a product, it joins the system.
  </Principle>
</Principles>

### Base components and slots

The base components are the small parts every larger component is built from.
The larger ones, such as Card, use slots: open areas a designer fills with
whatever the screen needs. A new need means filling a slot, and the component
stays the same size. Designers can vary a card without making a variant, and
engineers get the same freedom in code.

## Rollout, one product at a time

Product surfaces moved to the new system one at a time, and product work went
on while they did. Each surface had to be redesigned to fit. Teams used that
redesign to refresh their screens and fix problems they had been living with.

I own the question of what belongs in the system. I review how designers and
engineers use components and slots, coach designers through the system, and
keep the Figma library in step with the code.

## What changed

- The new Card shipped in 1.5 days. The old one took 2 weeks.
- 37 components rebuilt, with a working first version in 60 days.
- Card variants fell from 587 to 32, and button variants from 1,160 to 480.
- Three product suites now share one visual language, because they all build
  from the same base.
- Handoff documents shrank to what components can't say for themselves. What
  was left became the starting point for the
  [agentic handoff pipeline](/work/agentic-design-system), which cut spec
  writing from days to minutes.

## What I'd do next

- Connect the Figma components to their code with Code Connect, so designers
  see the real component instead of a description of it.
- Put the three rules inside the library, so they arrive with the components.
- Track adoption, so I can measure how much the system is used instead of
  guessing.
