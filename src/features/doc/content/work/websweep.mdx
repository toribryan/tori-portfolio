A design system is only ever a promise until a real product ships on it.
WebSweep is where the promise got tested.

Exam content leaks. It ends up in places the institution can't see, and they're
usually the last to know. WebSweep surfaces assessment content that has escaped
and turns a find into an action: a takedown, or swapping the affected questions
so the exam stays usable. It ships as one half of Vault by Proctorio, alongside
ScreenBlock.

The product design, the flows, and the product decisions belonged to the
product designer I worked alongside. This case study is about my part, which is
the system underneath it.

## Making the language hold under real pressure

The overhaul had set its principles on paper. No product logic in components.
No variants for hypothetical use. Start from the foundation and let the
foundation grow.

WebSweep is where those principles first met a product with its own needs.

My job was to make sure the language held. That the dashboard composed from the
system's tokens and components without forking them. That the spacing, type,
and color were the system's decisions and not the product's. And that when the
product needed something the system didn't have, the answer was a system
component, not a one-off.

Most of the dashboard composed cleanly. Two things didn't exist yet.

## The graph

The resolution-rate ring and the activity-over-time chart were the first data
visualizations the system had to carry. Which meant deciding how charts get
their color and type before anyone else needed one.

The tempting shortcut is to reach straight for the semantic tokens the rest of
the product uses. It's the wrong move, and it's a common one. A semantic token
maps a value to product meaning: warning, positive, disabled. A chart needs
tokens that map to a data role instead: series one, series two, a midpoint, a
missing value. The same red that means "error" in a form means "downward trend"
in a chart, and if both pull from the same token, the two meanings eventually
collide.

So I added a chart-token layer that inherits from the foundation rather than
forking a second palette off to the side. Chart color, type, and spacing
resolve through their own tokens, but those tokens still trace back to the same
primitives as everything else. The graph themes with the product without
borrowing tokens that were never meant to describe data. It's the approach
Carbon and the US Web Design System both land on, and it's the version that
survives a second and third chart type showing up later.

The payoff is quiet but real. The next product that needs a chart starts from a
component and a token layer instead of from scratch, and it starts already in
theme.

## The table that becomes cards

The findings table is dense by nature. Course, quiz, item, counts, status. It
reads well on a wide screen and falls apart on a phone.

There are two usual answers to that, and both are worse than they look.
Horizontal scroll hides half the data off the edge of the screen. A separate
mobile component means two things to build, two things to keep in sync, and two
places for them to drift apart.

The pattern that actually holds is collapsing each row into a card. That's the
well-worn move for dense tables on small screens, and the reason it works is
that cards keep every field for one item visible at a glance instead of
scrolled away. But there's a catch most versions miss: cards quietly drop the
header-to-value relationship a table gives you for free. On desktop the column
header says what a number means. On a card, that context has to travel with
the value, or a screen reader reads a bare figure with nothing attached.

So it's one component with two presentations. Rows on desktop. On mobile, each
row collapses into a card that keeps the same data, the same actions, and the
label-to-value pairing the table row had. One data model, one set of
behaviours, no fork.

This is the "let the foundation grow" principle actually doing its job. A real
pattern showed up in a real product, and the system absorbed it instead of
routing around it.

## What it proved

Both components went back into the library, so WebSweep left the system larger
than it found it.

The bigger thing it left is a reference. The first shipped answer to the
question every design system eventually has to answer out loud: what does the
language actually look like on a product? Every surface after this one gets to
start from that answer instead of guessing at it.

That's the version of proof I care about. Not that the system is finished, but
that it holds.
