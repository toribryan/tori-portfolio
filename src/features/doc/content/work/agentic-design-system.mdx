## Where I started

The [design system overhaul](/work/design-system-overhaul) at Proctorio rebuilt
the system for people. The question that came next was what happens when the
consumer is not a person.

Two agentic workflows were emerging at the same time, and the design system sat
between them. Engineering was beginning to generate implementations from
designs. Designers were beginning to prototype in code. Both were reaching for
the same system, neither was getting it right, and the explanations on offer
were guesses.

So I ran it as research, with our lead front-end engineer, rather than arguing
about it in the abstract.

## The experiment

Three things made it a test rather than a demo:

- Figma MCP as the connection between the design file and the model, so the
  model was reading the real design rather than a description of one.
- Prompt pipelines with controlled variation, so a difference in the output
  could be traced to a difference in the input instead of to the weather.
- The design system as the variable. Same design, same prompt, different
  amounts of structure exposed to the model.

The question was deliberately narrow. Given a design and a design system, can a
model produce an implementation that actually uses the system?

## What the first tests told us

No. Not without being told how.

A model reads a design perfectly well. It sees layout, spacing, color,
hierarchy, and the relationships between elements. What it cannot do is look at
a rectangle with a label and know that it is your Button, let alone know the
rules for using your Button correctly.

Handed a design and a system, it would:

- rebuild components from scratch instead of reaching for the ones that already
  existed
- hardcode the values it could see rather than the tokens that produced them
- assemble combinations the system deliberately does not allow

None of that is carelessness. The model was handed a picture and asked to
infer a contract. The information was in the design system the whole time, just
out of the model's reach.

A design system communicates through convention, apprenticeship and review, and
none of those survive contact with a machine consumer. That's also what Code
Connect is for: it lets a design point at its implementation, so the model stops
inferring and starts looking it up. I only understood that by testing it.

## The contracts I wrote

The fixes all did the same thing: move what the team knew out of people's heads
and into something a model can read.

**Tokens the agent can reason about.** Hand a model `#008b8b` and it will
hardcode that hex in forty places. So the agent only ever sees semantic tokens
named for their job (`color/action/primary`), never the primitives behind them
(`teal-500`). A rebrand updates one alias and everything downstream follows.

![The three-tier token architecture: primitives, semantics, component tokens](/case-studies/agentic-design-system-tokens.svg)

**Component metadata.** Prose docs are written for people. An agent needs JSON
per component covering props, relationships, the tokens it consumes, and usage
with anti-patterns. An agent can draft this, but it comes back about 80% right
and 20% generic. It lists the obvious anti-patterns and misses the ones that
bite, like "never use a destructive button in onboarding." That 20% is what the
team learned the hard way, and a person has to write it.

![Semantic token definitions layered on top of the raw primitives](/case-studies/agentic-design-system-semantic-tokens.svg)

**One source of truth.** The Figma library, the docs site and the token files
all resolve to one contract instead of competing, so the agent never has to
guess which to trust.

Once the system could be read by a machine, the handoff could be rebuilt around
that. It became the
[design skills infrastructure](/latest/design-skills-infrastructure), which
took spec production from days to under 30 minutes.

## What the research was missing

My own next steps from that project already pointed at the gap: measure it with
a standing benchmark, and make a component without its usage contract fail
review the way one without an accessible name would.

Both are about enforcement. Every fix I'd made was a contract the agent was
given. Nothing stopped an agent from ignoring it, and nothing told it when it
had. That's the part I got to build next.

## Where I am now: fibo

[fibo](/fibo) is my own design system, rebuilt in August 2026 on shadcn and Base
UI and published as a registry, so any project installs parts as source. Much
of it is built by Claude Code, working from the rules below. I set the rules,
and I review and merge what comes back.

The rules live in two kinds of places: written down where an agent will read
them, and enforced by something that runs.

| Rule                                       | Where the agent learns it | What enforces it                                                                                                 |
| ------------------------------------------ | ------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Five checks define done                    | `AGENTS.md`               | CI runs lint, format, Figma drift, build, typecheck and tests on every pull request                              |
| Every part installs cleanly                | `AGENTS.md`               | A smoke test installs each part into a fresh shadcn app and fails on classes that compile to nothing             |
| Accessible by default                      | `AGENTS.md`               | Every story renders in Chromium with axe set to fail on any violation                                            |
| Figma and code share names                 | `figma-drift` skill       | `pnpm figma:drift` compares the Figma snapshot with the CSS tokens and variants; every intended gap has a reason |
| Every part has metadata                    | `add-component` skill     | The build fails if a component is missing from `components.meta.json`                                            |
| Semantic tokens only, no opacity modifiers | `AGENTS.md`               | A read-only `component-reviewer` subagent reports violations with file and line                                  |
| Retiring a part never strands anyone       | `retire-component` skill  | One `deprecated` entry feeds the docs banner, catalog, registry and `llms.txt`, plus a tested codemod            |

That metadata check is the "fails review" step from my old next-steps list,
built for real.

One detail shows how the Figma side fits in. Figma silently forces a fill's
opacity to 100% when its color is bound to a variable, so a class like
`bg-destructive/10` has no Figma twin. Instead of living with the mismatch, I
named every one of those as its own token (`-subtle`, `-hover`, `-ring`). Now
Figma, the CSS and the agent all reach for the same word.

The proof is in the pull requests. An agent-written Voice memo component
(PR #86, about 1,570 lines) arrived with its stories, docs page, metadata entry
and changelog line, reported 192 unit tests and 204 story tests passing, and
took the "new" tag off the oldest part to stay under the limit of three. Nobody
had to catch what was missing, because the checks wouldn't let anything be
missing.

## What works best today

Agent support is table stakes now. In Kaelig Deloumeau-Prigent's
[State of AI in Design Systems](https://state-of-ai-in-design-systems.netlify.app/)
(21 systems, July 2026), 20 ship an MCP server, 19 ship agent skills and 16 keep
an AGENTS.md or CLAUDE.md in the repo. The useful question is which delivery
works. Here's what the evidence says, strongest first:

<Numbered>
  <Item title="Give agents real components, not descriptions of them.">
    In a CHI '26 study, serving installable components from a registry reached
    95.08% design-system compliance, ahead of pasting in full style guides or
    retrieved guideline sections.
  </Item>
  <Item title="Give them checks they can run and fix against.">
    In RepoComplianceBench (July 2026), agents opened policy files in only 3.5%
    of runs. With feedback from a check, compliance rose to 90 to 100%. shadcn's
    own linter reports near-zero violations after one correction round, because
    its errors say what to use instead.
  </Item>
  <Item title="Generate what the agent reads from the source.">
    Atlassian rebuilt its docs as typed, structured content that generates its
    MCP server, and reported 34% faster tasks and 16% fewer tokens. In their
    words, documentation that drifts from the code "is worse than no
    documentation at all."
  </Item>
  <Item title="Keep always-on context small and specific.">
    A compact docs index in AGENTS.md hit 100% on Vercel's eval, while agents
    skipped an available skill 56% of the time. Generic repo overviews added
    about 20% to cost with no gain in an ETH Zurich study.
  </Item>
  <Item title="Use one name for each decision on both sides.">
    The DTCG token spec reached its first stable version in October 2025, and
    Code Connect maps Figma components to code. Matching names are what make a
    drift check possible.
  </Item>
</Numbered>

The vendor numbers here (Atlassian, Storybook, Vercel) come from their own
benchmarks, so I read them as direction, not proof.

Here's how my original fixes hold up against that:

| What I did at Proctorio                     | How it holds up                                                                                                |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Lookup over inference, through Code Connect | Confirmed. The registry result is the same idea at full strength                                               |
| Agents see semantic tokens only             | Holds, and today a lint rule enforces it instead of hoping the agent never sees a primitive                    |
| JSON metadata per component                 | Holds. Generate the mechanical part from source, and keep people writing the usage rules                       |
| One canonical source, in Figma              | Partly. Installable code is what agents should consume, with Figma mapped to it and a drift check between them |

## What changed about the job

My job on a system like this is less about making each part and more about
writing the rules every part gets made by. A repeated comment in review becomes
a lint rule, a test or a line in `AGENTS.md`. What's left for review is what no
check can judge: intent, hierarchy, tone, and whether something is right for the
product.

## What I'd do next

- Measure it properly. This was my first next step at Proctorio and it's still
  open. fibo shows the mechanics work, but it has one maintainer and no
  baseline, so a standing benchmark is what would tell me whether the system is
  getting more legible over time or just differently broken.
